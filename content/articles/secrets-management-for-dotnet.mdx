A connection string committed to source control stays in the history forever, in every clone, on every laptop. Secrets management is about making the secure path the easy one at every stage of delivery.

## Introduction

<Statement type="fact">
.NET configuration is layered: later providers override earlier ones. That lets the same code read `ConnectionStrings:Default` from user secrets locally, from environment variables in CI and from a vault in production.
</Statement>

## Local development: user secrets

```bash
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Database=app;Username=app;Password=dev-only"
```

User secrets are stored outside the project directory, so they can't be committed by accident.

## CI: pipeline secrets

Store secrets in your CI system's secret store and expose them as environment variables. .NET maps `ConnectionStrings__Default` to `ConnectionStrings:Default`.

## Production: a vault

```csharp
// Example with Azure Key Vault; other vaults have equivalent configuration providers.
builder.Configuration.AddAzureKeyVault(
    new Uri(builder.Configuration["KeyVault:Uri"]!),
    new DefaultAzureCredential());
```

<Tip>
Use managed identities (or your platform's equivalent) so the application authenticates to the vault without a secret of its own.
</Tip>

## Security

<Warning>
If a secret has ever been committed, treat it as compromised. Rotate it — deleting the file or rewriting history is not enough.
</Warning>

- Add secret scanning to CI so leaks are caught before merge.
- Rotate secrets on a schedule, and design apps to pick up rotated values without a redeploy.
- Never log configuration objects wholesale.

## Conclusion

Same configuration keys, different providers per environment. The application code never needs to know where a secret came from.
